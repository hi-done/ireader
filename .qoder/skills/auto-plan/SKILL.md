# auto-plan 功能方案设计

将「需求澄清 → 代码调研 → 关键决策确认 → 成稿 specs/ → 自检 → 展示待确认」流程标准化，全程中文。本 skill 只产出设计文档：**未经用户确认，不修改任何源码、不进入实施**。

进度清单：

```
- [ ] 步骤 1 需求澄清与拆解
- [ ] 步骤 2 代码调研（基于事实）
- [ ] 步骤 3 关键决策交互确认
- [ ] 步骤 4 成稿 specs/<功能名>设计方案.md
- [ ] 步骤 5 方案自检
- [ ] 步骤 6 展示摘要并等待确认
```

前置：调研用 ireader-architecture 定位模块；成稿遵守 ireader-code-conventions（Result 契约、命名、工程红线）；实现路径引用 ireader-dev-tasks 的任务编号；确认后的实施阶段同样按 ireader-dev-tasks 执行。

## 步骤 1：需求澄清与拆解

1. 把用户诉求拆成功能点，每点给出「设计落点 + 验收方式」；无法验收的需求不算拆解完成，向用户追问补充。
2. 划定「非目标」（本期不做及原因），防止实施阶段范围蔓延。
3. 判明功能类型（数据层 / IPC 能力 / 渲染层与 UI / 阅读器行为 / 组合），决定调研重点与文档章节取舍。

## 步骤 2：代码调研（必须基于事实）

1. 先读一遍 `specs/阅读时间统计功能设计方案.md`，作为行文风格与详略程度的基准。
2. 用 ireader-architecture 定位相关模块；排查现有 store / service / 组件 / repo / IPC 通道中的可扩展点，优先扩展现有实现，不重复造。
3. 输出受影响面清单（按 electron/、shared/、src/ 分组），并标出高影响改动：IPC 契约变更、DB schema 迁移、新增依赖。
4. 方案中引用的现有文件名、函数名、字段名一律经 Read/Grep 核实，禁止凭印象引用。

## 步骤 3：关键决策交互确认

命中以下任一情况，用 AskUserQuestion 向用户确认（合并为 1~3 个问题，不逐条问）：

- 功能边界与范围取舍（本期做 / 不做）；
- 数据模型或持久化方式存在多个可行选择（新建表 vs 扩展表、SQLite vs localStorage 等）；
- UI / 交互存在多种风格方案；
- 需要新增 npm 依赖（工程红线：先征询）；
- DB 迁移或 IPC 契约变更的影响面取舍。

确认结果写入文档「关键决策」表：决策 / 选择 / 理由。理由写取舍依据（为什么不选另一方案），不复述选择本身。

## 步骤 4：成稿 specs/<功能名>设计方案.md

1. 位置与命名：`specs/<功能名>设计方案-日期.md`（中文文件名，与现有文档同级同风格，新增日期格式为20261020）。
2. 文档头固定引用块四行：状态（设计稿）、目标版本（读 package.json 当前 version ，版本号不变，由用户自行发版时确定）、范围、实现约束（引用 ireader-dev-tasks 与 ireader-code-conventions）。
3. 章节骨架与写作要求（按功能类型裁剪，不涉及即删，不留空章节）：

| 章节 | 写作要求 |
|------|----------|
| 一、需求拆解与验收标准 | 表格「原始需求 / 设计落点 / 验收方式」；末尾一句可量化的「核心验收口径」 |
| 二、非目标（本期不做） | 不做项 + 原因 |
| 三、总体设计 | ASCII 分层数据流图（渲染层 → IPC → 主进程 → DB）；关键决策表 |
| 四、核心算法 / 口径 | 涉及算法或统计口径时：TS 伪代码 + 边界场景防护表 |
| 五、数据模型 | 涉及 DB 时：MIGRATIONS 末尾追加式迁移 SQL（`-- vN: 说明`）+ repo 接口签名与关键 SQL |
| 六、IPC 契约 | 涉及 IPC 时：shared/types.ts 新增类型（中文 JSDoc）+ 通道表（通道/入参/返回/说明）+ 服务层校验规则 |
| 七、主进程实现 | service 职责划分 + handler 编排；handler 只做编排不塞业务 |
| 八、渲染层实现 | store / service / view 接缝点，按 ireader-dev-tasks 任务 D/E 归属规则指明文件与接线位置 |
| 九、页面 / 交互设计 | 涉及 UI 时：路由入口、布局 ASCII 草图、视觉规范（引用主题 CSS 变量）、空态 / 加载态 / 错误态 |
| 十、文件变更清单 | 按 electron/、shared/、src/ 分组表格（文件 / 变更）；末尾列「不改动」清单 |
| 十一、测试计划 | 单测用例表（中文用例 / 断言）+ 手工冒烟清单（含 `npm run typecheck`、`npm test`、`npm run dev` 步骤） |
| 十二、实施顺序（里程碑） | M1..Mn 按依赖排序，每条给可执行的完成标准 |
| 十三、风险与取舍记录 | 表格：项 / 取舍 / 影响与备注；写明接受理由与将来扩展点 |

4. 硬性要求：
   - 纯离线红线：方案不得引入网络资源；拟新增 npm 依赖必须已在步骤 3 获用户确认。
   - 契约类型只定义在 `shared/types.ts`；IPC 通道命名「域:动作」，按 ireader-dev-tasks 任务 A 的六步链路写清改动顺序。
   - 埋点 / 计时 / 全局监听类逻辑单点化（如阅读场景只在 ReaderView.vue 接线一次），避免 PDF / EPUB 双引擎各自实现导致重复统计。
   - 未决问题不允许含糊带过：要么在步骤 3 问清，要么明确列入「非目标」或「风险与取舍」。
   - 小改动可精简章节，但六个步骤不可跳过。

## 步骤 5：方案自检（展示前必做）

- [ ] 每条需求都有设计落点与验收方式，无孤儿需求
- [ ] 引用的现有文件 / 接口 / 字段均经 Read/Grep 核实，与源码一致
- [ ] 无网络依赖；拟新增依赖已获用户确认
- [ ] DB 迁移为 MIGRATIONS 末尾追加，未修改已发布项（若涉及）
- [ ] IPC 通道命名「域:动作」，新类型在 `shared/types.ts`（若涉及）
- [ ] 文件变更清单与正文各章落点一一对应（无清单外改动、无正文提了清单漏了）
- [ ] 测试计划含可执行命令与手工冒烟步骤
- [ ] 关键决策均在步骤 3 经用户确认，未混入未经确认的决策

## 步骤 6：展示摘要并等待确认（必须）

1. 展示：文档路径、需求拆解表、关键决策表、文件变更清单概览、里程碑、风险取舍要点。
2. 明确询问用户：方案是否通过？需要调整哪些部分？用户提出修改时更新文档后再次确认。
3. 红线：未经确认不得开始实施（不写任何源码）。确认后告知用户可按里程碑进入实施（实施遵循 ireader-dev-tasks）；实施中若需偏离方案，先回写文档再改代码。
