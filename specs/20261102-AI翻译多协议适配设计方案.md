# AI 翻译多协议适配设计方案

> 状态：设计稿（待确认）
> 目标版本：v1.4.2（版本号不在本方案内变更，由发版时确定）
> 范围：AI 配置项的协议字段（OpenAI 兼容 / Anthropic 兼容）、主进程请求层按协议分支、配置页协议选择与服务商预设、三语言文案；不含阅读页交互与数据库结构变更
> 实现约束：遵循 `ireader-dev-tasks`（任务 A/B/D/E 的接线顺序）与 `ireader-code-conventions`（Result 契约、契约类型只定义在 `shared/types.ts`、中文注释、纯离线）

## 一、需求拆解与验收标准

| # | 原始需求 | 设计落点 | 验收方式 |
|---|----------|----------|----------|
| 1 | 支持 Anthropic Messages 协议（`/v1/messages`），可直接用 `https://api.deepseek.com/anthropic` 这类端点 | `AiProviderConfig.protocol: 'openai' \| 'anthropic'`；`aiProtocol.resolveEndpoint` 按协议拼路径 | 配置 Anthropic 协议 + `https://api.deepseek.com/anthropic`，框选翻译成功落库 |
| 2 | 图片入参按协议转换 | `buildChatRequest`：OpenAI 用 `image_url` + data URL，Anthropic 用 `image` + `source.base64` | 两种协议下同一张框选图都能拿到译文 |
| 3 | 响应结构按协议取值 | `extractReplyText(protocol, json)`：OpenAI 取 `choices[0].message.content`，Anthropic 取 `content[]` 中 `type === 'text'` 的块 | 两种协议都能解析出译文与建议字号 |
| 4 | 配置页可显式选择协议，旧配置不受影响 | 表单新增「接口协议」下拉（默认 OpenAI 兼容）；`normalizeAiSettings` 缺省补 `'openai'` | 升级后未编辑的旧配置仍按 OpenAI 协议正常翻译 |
| 5 | 降低首次配置成本 | 表单新增「填入 DeepSeek 预设」按钮（`https://api.deepseek.com` + `deepseek-flash` + OpenAI 协议），只写入草稿不保存 | 点击后地址、模型名、协议自动填好，可改后再保存 |
| 6 | 鉴权同时兼容官方与中转站 | Anthropic 分支同时发 `x-api-key` 与 `Authorization: Bearer`，并带 `anthropic-version` | 官方 Anthropic 与只认 Bearer 的中转站都能通过「测试连接」 |
| 7 | 错误提示与现有口径一致 | 复用 `AI_AUTH_FAILED` / `AI_REQUEST_FAILED`，不新增错误码 | 错误 Key 在两协议下都提示中文鉴权失败，可删除 |

**核心验收口径**：在配置页新增一条「Anthropic 协议 + `https://api.deepseek.com/anthropic` + `deepseek-flash`」配置并设为当前使用，点「测试连接」返回耗时且无报错，随后在阅读页框选一格对白得到译文并落库；同一条机器上把协议切回 OpenAI 兼容 + `https://api.deepseek.com` 仍可翻译；升级前已存在的配置（无 `protocol` 字段）不做任何编辑即可继续翻译。

## 二、非目标（本期不做）

- **不做 OpenAI Responses API（`/v1/responses`）与 Gemini 原生协议**：当前两类需求集中在「对话补全」形态，Responses API 的请求体与流式语义另成体系；Gemini 的图片走 `inline_data` 且参数命名差异大。二者按 §13 的扩展点后续单独评估。
- **不做流式输出（SSE）**：Anthropic 的 `stream: true` 需要在主进程解析事件流并回流渲染层，与现有「一次请求一次返回」的落库时序不兼容，收益仅是首字更快。
- **不做 Anthropic 的 `system` 字段拆分与 `tools`**：提示词仍整体放在 user 消息里，不引入工具调用。（`thinking` 开关**已做**：见 §3「思考模式」与 §4.2 —— DeepSeek 默认开思考会把 `max_tokens` 吃光导致正文为空，必须显式关闭。）
- **不做 URL 自动推断协议**：地址字符串特征（`/anthropic`、域名含 anthropic）在中转站上不可靠，改为显式选择（§13 记录该取舍）。
- **不改动阅读页**：`ReaderView.vue`、`AiTranslationLayer.vue`、`stores/aiTranslation.ts` 一行不动，框选与覆盖层逻辑与协议无关。
- **不改动数据库结构**：配置存在 `settings` 表的 JSON 文本里，不新增列、不追加迁移。
- **不新增 npm 依赖**（不引入 `@anthropic-ai/sdk` 或 `openai` SDK）：两协议都是 JSON over HTTP，现有全局 `fetch` 足够；工程红线要求新增依赖先征询。

## 三、总体设计

```
┌─ 配置页 AiConfigView.vue ──────────────────────────────────────────┐
│ 「填入 DeepSeek 预设」按钮（只填草稿） → draft{ name baseUrl apiKey model protocol } │
│ 协议下拉：openai / anthropic                                       │
└───────────────────────┬───────────────────────────────────────────┘
                        │ ipc settings:patch（整对象覆盖 settings.ai）
                        ▼
        settingsService.patch → normalizeAiSettings（缺省补 'openai'）
                        ▼
        settingsRepo（SQLite settings 表，JSON 文本，无 schema 变更）
                        ▲
                        │ settingsRepo.getAll().ai.providers[i]
                        │
┌─ 主进程 aiService ─────┴───────────────────────────────────────────┐
│ activeProvider() → { protocol, baseUrl, apiKey, model }            │
│ translate / test：统一内容块 [{ type:'text' } | { type:'image' }]  │
└───────────────────────┬───────────────────────────────────────────┘
                        ▼
        aiProtocol.buildChatRequest(provider, content, maxTokens)
          ├─ resolveEndpoint：…/chat/completions 或 …/v1/messages
          ├─ headers：Bearer ｜ x-api-key + Bearer + anthropic-version
          └─ body：image_url 块 ｜ image/source 块
                        ▼
        fetch（60s 超时，仅用户动作触发，无后台轮询）
                        ▼
        aiProtocol.extractReplyText(protocol, json)
                        ▼
        aiReply.extractReply → { text, fontRatio }
```

**关键决策**

| 决策 | 选择 | 理由 |
|------|------|------|
| 协议的表达方式 | 配置项内显式 `protocol` 字段 | 中转站地址无规律，按地址推断会误判且用户无法覆盖；显式字段可校验、可归一、可持久化，且后续加第三种协议只是加枚举值 |
| 旧配置兼容 | `normalizeAiSettings` 缺省补 `'openai'`，无 DB 迁移 | 协议存在 settings JSON 里而非表列，归一化即可完成「迁移」；未编辑的旧配置零感知 |
| 请求层组织 | 新增 `electron/services/aiProtocol.ts` 放纯函数 | `aiService` 直连 repo 与 `fetch`，逻辑混在一起无法单测；抽成纯函数后 URL / 头 / 体 / 取值四段行为都能用 Vitest 覆盖，延续 `aiReply.ts` 的分工先例 |
| 鉴权头策略 | Anthropic 分支双发 `x-api-key` 与 `Authorization: Bearer` | 官方只认 `x-api-key`，部分第三方网关只认 Bearer；双发同时覆盖，代价仅一个冗余头（官方与 DeepSeek 兼容层均不因此报错） |
| 参数取值 | 两协议统一 `temperature: 0.2` + `max_tokens: 1500` | Anthropic 的 `max_tokens` 必填，统一传值可避免分支参数漂移；原 `800` 在长多行对白 + JSON 包装时偏紧，上调到 1500 |
| 思考模式 | 请求体显式 `thinking: { type: 'disabled' }`；遇到 400 且 body 提到 thinking 时去掉该字段重试一次 | DeepSeek 默认开启思考（effort 默认 high），思维链走 `reasoning_content` 并占用 `max_tokens`，实测 800 被吃光 → `content` 为空、译文解析失败；OpenAI 官方不认该字段会 400，故用一次重试兼容两类端点 |
| 响应取值 | Anthropic 只拼接 `type === 'text'` 的块 | 思考模式下 `content` 会混入 `thinking` 块，混入会污染 `extractReply` 的 JSON 抽取 |
| 服务商预设 | 仅 DeepSeek 单预设，按钮形态，只填草稿 | 实际只接 DeepSeek，多给几个反而要判断选哪个；单选项的下拉是反模式，改成一个按钮一次点击。仍不直接保存，避免模型名失效时写入脏配置 |
| 依赖策略 | 不新增依赖，继续用全局 `fetch` | 两协议都是「JSON 进、JSON 出」，SDK 只会增加体积与 Electron 打包复杂度 |

## 四、协议口径与核心算法

### 4.1 URL 归一

`baseUrl` 由用户手填，尾斜杠与路径冗余都可能出现，统一先裁剪再判定：

| 协议 | 用户填写示例 | 归一结果 |
|------|--------------|----------|
| openai | `https://api.openai.com/v1` | `https://api.openai.com/v1/chat/completions` |
| openai | `https://api.deepseek.com` | `https://api.deepseek.com/chat/completions` |
| openai | `https://api.openai.com/v1/chat/completions/` | `https://api.openai.com/v1/chat/completions`（已含路径则不重复拼接） |
| anthropic | `https://api.anthropic.com` | `https://api.anthropic.com/v1/messages` |
| anthropic | `https://api.deepseek.com/anthropic` | `https://api.deepseek.com/anthropic/v1/messages` |
| anthropic | `https://api.anthropic.com/v1` | `https://api.anthropic.com/v1/messages`（已含 `/v1` 则不重复） |

```ts
/** 拼请求地址：先裁尾斜杠；anthropic 已含 /v1 时不重复追加 */
export function resolveEndpoint(provider: AiProviderConfig): string {
  const base = provider.baseUrl.trim().replace(/\/+$/, '')
  if (provider.protocol === 'anthropic') {
    return /\/v1$/i.test(base) ? `${base}/messages` : `${base}/v1/messages`
  }
  return /\/chat\/completions$/i.test(base) ? base : `${base}/chat/completions`
}
```

### 4.2 请求体映射

内容以中间表示传入，避免 `aiService` 里拼协议细节：

```ts
export type AiChatContent = { type: 'text'; text: string } | { type: 'image'; base64: string }
```

| 内容 | OpenAI 兼容 | Anthropic 兼容 |
|------|-------------|-----------------|
| 文本 | `{ type: 'text', text }` | `{ type: 'text', text }` |
| 图片 | `{ type: 'image_url', image_url: { url: 'data:image/jpeg;base64,…' } }` | `{ type: 'image', source: { type: 'base64', media_type: 'image/jpeg', data } }` |
| 消息 | `messages: [{ role: 'user', content: 块数组 }]` | 同左（Anthropic 同样接受块数组） |
| 采样参数 | `temperature: 0.2`、`max_tokens: 1500` | 同左（`max_tokens` 必填） |
| 思考开关 | `thinking: { type: 'disabled' }` | 同左（Anthropic 格式同名同结构；端点在 400 中提及 thinking 时由 `requestChat` 去掉后重试） |

头部：

| 协议 | `Content-Type` | 鉴权 | 其它 |
|------|----------------|------|------|
| openai | `application/json` | `Authorization: Bearer <key>`（key 为空时不发，兼容 Ollama 等本地服务） | — |
| anthropic | `application/json` | `x-api-key: <key>` + `Authorization: Bearer <key>`（key 为空时两个都不发） | `anthropic-version: 2023-06-01` |

### 4.3 响应取值

| 协议 | 取值路径 | 容错 |
|------|----------|------|
| openai | `choices[0].message.content` | 字符串直接用；分段数组按 `text` / `content` 字段拼接（沿用现有实现） |
| anthropic | `content[]` 中 `type === 'text'` 的 `text` 拼接 | 非数组返回 `''`；`thinking` / `tool_use` 块被过滤；多 text 块直接相连 |

出参 `''` 会被 `aiReply.extractReply` 归一为空文本，渲染层据此展示「未识别到文字内容」灰色兜底，与 OpenAI 分支行为一致。

### 4.4 边界防护

| 场景 | 行为 |
|------|------|
| `baseUrl` 无 `http(s)://` | 配置页校验期拦截（现有 `validate` + 服务端 `validateProvider` / `assertAiPartial`） |
| `baseUrl` 已含完整路径 | 不重复拼接（§4.1） |
| `apiKey` 为空 | 两协议都不发鉴权头，Anthropic 仍发 `anthropic-version` |
| `protocol` 缺失或非法（读路径） | `normalizeAiSettings` / `validateProvider` 回退 `'openai'`，不阻断使用 |
| `protocol` 非法（写路径） | `assertAiPartial` 抛 `INVALID_PARAMS`，阻止脏值落盘 |
| 响应无 `content` / 无 text 块 | 返回 `''` → 灰色兜底，不落库 |
| HTTP 401 / 403 | `AI_AUTH_FAILED`（Anthropic 的 `authentication_error` 同样是 401） |
| HTTP 429 / 529 / 其它 4xx-5xx | `AI_REQUEST_FAILED`，文案带状态码，日志留响应前 300 字 |
| 请求超时 | 60s（翻译）/ 30s（测试连接），沿用现有常量 |

## 五、配置模型与归一化

`AiProviderConfig` 新增必填字段（契约类型只在 `shared/types.ts`）：

```ts
/** 接口协议：openai = /chat/completions；anthropic = /v1/messages（DeepSeek 的 /anthropic 端点属于此类） */
export const AI_PROTOCOLS = ['openai', 'anthropic'] as const
export type AiProtocol = (typeof AI_PROTOCOLS)[number]

export interface AiProviderConfig {
  id: number
  name: string
  /** 基础地址，如 https://api.openai.com/v1 或 https://api.deepseek.com/anthropic */
  baseUrl: string
  apiKey: string
  model: string
  /** 请求协议，缺省按 openai 处理 */
  protocol: AiProtocol
}
```

`normalizeAiSettings` 在构造每个 provider 时补默认值：

```ts
protocol: (AI_PROTOCOLS as readonly string[]).includes(p.protocol as string)
  ? (p.protocol as AiProtocol)
  : 'openai',
```

`settingsRepo.getAll()`（读）与 `settingsService.patch()`（写）都已过 `normalizeAiSettings`，因此旧配置无需任何迁移：**本方案不涉及 `MIGRATIONS` 变更**。

## 六、IPC 契约

**不新增通道**，只扩展既有通道的载荷与校验：

| 通道 | 入参变化 | 返回 | 说明 |
|------|----------|------|------|
| `settings:patch` | `Settings.ai.providers[i]` 增加 `protocol` | `Result<Settings>` | 写入口，`assertAiPartial` 严格校验协议白名单 |
| `ai:test` | `{ provider }` 中增加 `protocol` | `Result<AiTestResult>` | 走与翻译同一条 `buildChatRequest` 分支，保证「测试连接」通过即翻译可通 |
| `ai:translate` | 无变化 | `Result<AiTranslateResult>` | 协议由主进程从已保存配置读取，渲染层不感知 |

校验规则分层：

| 位置 | 函数 | 策略 |
|------|------|------|
| 写入口 | `assertAiPartial`（`electron/ipc/handlers.ts`） | `protocol` 不在 `AI_PROTOCOLS` 中 → `INVALID_PARAMS`「配置接口协议取值无效」 |
| 测试连接 | `aiService.validateProvider` | 非法/缺失 → 回退 `'openai'`（草稿未经过 normalize，宽松处理避免凭空报错） |
| 读路径 | `normalizeAiSettings` | 非法/缺失 → `'openai'` |
| 翻译 | `aiService.activeProvider` | 不校验：配置已由写入口与读路径保证，避免请求期多一次判断 |

## 七、主进程实现

### 7.1 新增 `electron/services/aiProtocol.ts`

职责：把「协议」压缩成一个入参，产出可直接 `fetch` 的三元组，并把响应文本取回。除 `fetch` 外无副作用，可全量单测。

```ts

const ANTHROPIC_VERSION = '2023-06-01'

export type AiChatContent = { type: 'text'; text: string } | { type: 'image'; base64: string }

export interface AiChatRequest {
  url: string
  headers: Record<string, string>
  body: unknown
}

export function resolveEndpoint(provider: AiProviderConfig): string { /* §4.1 */ }

/** 按协议构造请求：头部与内容块结构不同，采样参数一致 */
export function buildChatRequest(
  provider: AiProviderConfig,
  content: AiChatContent[],
  maxTokens: number,
  options?: { thinkingControl?: boolean }
): AiChatRequest { /* §4.2：body 用 toOpenAiBlock / toAnthropicBlock 映射；默认加 thinking:{type:'disabled'} */ }

/** 解析失败日志用的响应结构摘要（finish_reason / stop_reason 与字段名，不含正文） */
export function describeChatResponse(protocol: AiProtocol, json: unknown): string { /* §4.3 */ }

/** 按协议取回复文本：anthropic 过滤 thinking 等非 text 块 */
export function extractReplyText(protocol: AiProtocol, json: unknown): string { /* §4.3 */ }
```

### 7.2 改造 `electron/services/aiService.ts`

三处改动，其余逻辑（校验、超时、错误映射、落库编排）不动：

1. `requestChat(provider, content: AiChatContent[], timeoutMs)`：删掉内部 URL 拼接与 header 组装，改为「`postChat` 单次 POST + 按需重试」
   ```ts
   let res = await postChat(buildChatRequest(provider, content, MAX_OUTPUT_TOKENS), timeoutMs)
   if (res.status === 400 && /thinking/i.test(res.text)) {
     // 端点不认识 thinking 字段（如 OpenAI 官方）：去掉后重试一次
     res = await postChat(buildChatRequest(provider, content, MAX_OUTPUT_TOKENS, { thinkingControl: false }), timeoutMs)
   }
   ```
   `postChat` 只做 `fetch` + `res.text()`，状态码与正文交上层统一映射错误；`MAX_OUTPUT_TOKENS = 1500` 两协议共用。
2. `translate`：内容块改为中间表示
   ```ts
   [{ type: 'text', text: prompt }, { type: 'image', base64: image }]
   ```
   取值改为 `extractReply(extractReplyText(provider.protocol, json))`。
3. `validateProvider`：返回值补 `protocol`（非法/缺失回退 `'openai'`），保证 `ai:test` 的草稿能带协议进入请求层。

`electron/ipc/handlers.ts` 的 `assertAiPartial` 增加一行白名单校验（§6）。

## 八、渲染层实现

只改 `src/views/AiConfigView.vue`（配置页），阅读页零改动：

| 接缝点 | 改动 |
|--------|------|
| `draft` | 增加 `protocol: 'openai' as AiProtocol`，`openNew` 填默认、`openEdit` 取 `p.protocol`（旧配置已由主进程 `normalizeAiSettings` 补齐，无需前端兜底） |
| `draftProvider()` | 返回值带 `protocol: draft.protocol` |

| 地址占位符 | `baseUrlPlaceholder` computed：openai → `https://api.openai.com/v1`，anthropic → `https://api.anthropic.com`，随协议切换 |
| 服务商预设 | `DEEPSEEK_PRESET` 常量 + `applyDeepseekPreset()`：把 name / baseUrl / model / protocol 写入 `draft` 后 `resetFeedback()`；不动已填的 apiKey |

| `validate()` | 不新增校验：`protocol` 由下拉约束，服务端仍兜底 |

唯一预设（值随服务商迭代，仅作初值）：

| name | baseUrl | model | protocol |
|------|---------|-------|----------|
| `DeepSeek` | `https://api.deepseek.com` | `deepseek-flash` | `openai` |

## 十三、风险与取舍记录

| 项 | 取舍 | 影响与备注 |
|----|------|------------|
| Anthropic 无 JSON mode | 仍靠提示词约束 + `extractReply` 容错抽取 | 偶发输出非 JSON 时降级为「未识别」兜底，不落库；不为此加二次请求重试（重试会重复计费） |
| 双发鉴权头 | 同时发 `x-api-key` 与 `Bearer` | 极严格的网关可能对重复鉴权告警，概率极低；若真遇到，退化为按协议只发 `x-api-key` 的开关（扩展点） |
| 预设模型名会过时 | 预设只写入初值 + 表单提示「按官方文档核对」 | DeepSeek 旧视觉名 `deepseek-v4-flash-vision-exp` 已下线并由新名承接，模型名会继续迭代；不硬编码可用性判断，避免预设失效导致「测试连接」必失败 |
| 不做地址自动推断 | 显式协议下拉 | 中转站地址不可枚举，推断不可靠且用户无法覆盖；代价是首次配置多一次点击 |
| OpenAI 分支 URL 顺带容错 | 已含 `/chat/completions` 时不再拼接 | 行为增强（此前会拼成双路径），对既有正确配置无影响；测试 3、4 覆盖 |
| `max_tokens: 1500` 上限 | 两协议统一 | 关闭思考后 1500 足够覆盖多行对白与 JSON 包装；仍非硬保证，真正溢出由 `aiReply` 的截断/抢救逻辑兜底 |
| `thinking` 字段兼容性 | 默认带、400 时去掉重试一次 | 不认识该字段的端点（OpenAI 官方）会返回 400 并在 body 提到 thinking，据此判定后重试，代价是极端情况下多一次往返；比按域名硬编码「是不是 DeepSeek」更通用 |
| 第三/第四协议的扩展 | `AiProtocol` 枚举 + `aiProtocol.ts` 内两处 switch | 新增 Gemini / Responses API 只需扩枚举、加 `resolveEndpoint` 与两个映射分支，`aiService` 与 UI 仅需加选项 |
| 图片格式固定 JPEG | 渲染层本就只产出 JPEG | 若将来支持 PNG 截图，需给 `AiChatContent.image` 加 `mediaType` 字段（当前不做） |
