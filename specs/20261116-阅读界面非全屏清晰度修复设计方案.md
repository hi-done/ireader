## 一、需求拆解与验收标准

| # | 原始需求 | 设计落点 | 验收方式 |
|---|----------|----------|----------|
| 1 | 阅读界面非全屏时画面很模糊，从全屏退出后开始模糊 | 全屏状态变化 → 等合成器尺寸落定 → 强制重栅格 + 按实测尺寸重渲（PDF 重渲页组 / EPUB 重建 rendition / 纵向重排），并由主进程复位页面缩放（`window:resetPageScale`） | 手工：全屏 ↔ 窗口来回切换 5 次，三种格式均无肉眼可见发虚 |
| 2 | 三种格式（PDF / EPUB 文字 / 漫画）都应清晰，不只修一条路径 | 修复落在**共用层**（渲染尺寸口径 + 全屏切换钩子 + 主进程复位），三个视图只做接线，各自不重复实现 | 逐格式在窗口化 / 最大化 / 全屏三态下各截一次画面比对 |
| 3 | 只有页面内容发虚、顶栏按钮文字清晰（不是全窗口问题） | 判定为阅读内容层的栅格/尺寸问题：诊断读数用 `canvas 后备像素 : CSS 显示尺寸 : dpr` 三者比例 + `visualViewport` 双口径定位 | 采样读数 `verdict` 与肉眼判断一致 |
| 4 | 先加诊断读数和开关，再定策略 | 生产可用的一次性采样（写主进程日志）+ `SHARPNESS_FIX` 开关常量（各修复项可单独关闭做二分） | 关闭某项后现象复现，说明该项确实是有效杠杆 |
| 5 | 渲染尺寸与显示盒必须严格 1:1（后续不再复发） | 渲染目标改用容器实测 `clientWidth/clientHeight`；像素对齐统一到 `renderGeometry.fitRenderBox`；`devicePixelRatio` 纳入位图缓存签名并监听变化 | 单测：`|pixel/css/dpr − 1| ≤ 0.5%`；改系统缩放 100%→150% 后画面自动重渲且清晰 |

**核心验收口径**：在任意窗口尺寸、任意缩放档位、任意显示缩放下，显示 canvas 满足 `|canvas.width / rect.width / dpr − 1| ≤ 0.005` 且 `visualViewport.scale === 1`；从全屏退出后 300ms 内画面清晰度与全屏态一致（无肉眼可辨的发虚）。

## 二、非目标（本期不做）

- **不做超采样（2x 渲染）**：内存与渲染耗时约翻倍，且当前证据指向"尺寸/栅格错位"而非"位图分辨率不足"。等 §4.3 诊断读数落地后按实测数据单独决策（开关位已预留，见 §3.3）。
- **不新增用户可见设置项**：新增清晰度/画质开关会牵动 `Settings` 契约与设置页 UI；本期以常量开关 + 诊断读数替代，避免为未定结论先落持久化契约。
- **不改翻页动画（`pageCurl.ts`）与卷曲几何**：动画路径已按"实际显示矩形"归一化，与本次问题（静态画面）无交集，改动会引入新的几何回归。
- **不改 pdf.js / epub.js 引擎版本与 CMap 资源链路**：与清晰度无关（引擎升级另有 Chromium 版本约束）。
- **不做 macOS 专项验证**：本机无 mac 环境；`titleBarStyle: hidden` 下窗口尺寸链路不同，风险与取舍见 §12。

## 三、总体设计

### 3.1 已核实的事实与推论（调查结论）

调查基于当前 `main`（`a21f8ba`）。以下为 Read/Grep 核实过的既成事实：

| # | 事实（源码依据） | 对本次问题的影响 |
|---|------------------|------------------|
| F1 | `src/services/pdf.ts:146-156`：渲染 scale 取 `targetWidth/targetHeight`，再乘 `dpr` 写入 `canvas.width/height`，CSS 尺寸用 `viewport.width / dpr` 反推（浮点、未对齐） | 后备像素与 CSS 尺寸的比例只**近似**等于 dpr，存在 ≤1px 的取整偏差 |
| F2 | `ReaderView.vue:1028-1046`：`zoomRenderOptions()` 取 `window.innerWidth/innerHeight`，取不到 `.page-area` 的实测尺寸 | 渲染尺寸与显示容器之间存在"两个尺寸真相"，二者不同步的瞬间（全屏切换）就会错位 |
| F3 | `ReaderView.vue:1058-1060`：`cacheSignature()` 为 `v2:${innerWidth}x${innerHeight}:${mode}:${zoomMode}:${zoomScale}`，**不含 dpr** | dpr 变化（跨显示器、系统缩放调整）时可能命中旧 dpr 位图 → 显示时被重采样 |
| F4 | `ReaderView.vue:1527-1541`、`EpubReaderView.vue:1568-1585`：全屏切换只依赖 `window.resize` 事件（200ms 防抖）触发重渲/重排；`VerticalScrollView.vue:522-526` 依赖 `ResizeObserver` | 三条路径**理论上**都能自愈 → 若退出全屏后持续发虚，说明残留问题不在"位图尺寸"层，而在**合成器栅格层**（页面被按旧尺寸栅格化后整体缩放） |
| F5 | `ReaderView.vue:1859-1894`、`:1917-1922`：`.page-area` / `.page-wrap` / `.page-wrap canvas` 均无 CSS 钳制、无 `transform`、无 `will-change`；canvas 不是 flex item（父级 `.page-wrap` 为 `display:block`） | 排除"CSS 钳制压扁"与"flex 压缩"两个历史缺陷类型的复发 |
| F6 | `src/services/imagePage.ts:22-40` 与 `pdf.ts:144-156` 各自实现一套等比缩放口径 | 同一口径两份实现，像素对齐修复必须收敛成单点，否则只修一半 |

**推论**：F4 是本问题的关键分叉点。三条渲染路径在窗口尺寸变化后都会自我重渲，因此"退出全屏后持续模糊"最可能的成因是——窗口全屏切换后，Chromium 的**页面/视觉缩放或合成层栅格尺寸**停留在旧值（例如仍按 1920×1080 的栅格缩放到 1280×770 的窗口），这时 DOM 布局与 canvas 后备像素都是对的（诊断读数 ratio=1），但整层被 GPU 缩小 → 页面内容（canvas、iframe 文字）整体发虚，而顶栏因带 `backdrop-filter`（`ReaderView.vue:1721`）自建渲染表面重新栅格，反而是清晰的——与用户描述完全吻合。

因此方案采取"**先可观测、再对症**"的顺序：M1 落地诊断读数把 `ratio` 与 `visualViewport.scale` 分离显示，确认是"位图尺寸错位"还是"合成层缩放"；M2/M3 把两种成因的修复都做掉（都是幂等低成本项，且互不冲突），M4 用开关做二分确认有效杠杆。

## 四、清晰度口径与诊断算法（核心）

### 4.1 清晰度不变式

一条画面"清晰"的必要条件拆成三条独立可测的子式：

1. **位图不变式**（渲染色）：`canvas.width / canvas.getBoundingClientRect().width / dpr ≡ 1`（容差 0.5%）。不满足 → 位图被 CSS 或布局重采样。
2. **页面缩放不变式**（合成层色）：`visualViewport.scale ≡ 1` 且 `visualViewport.width ≡ innerWidth`。不满足 → 整个页面被浏览器层缩放，此时位图不变式仍可能成立（正是 F4 推论的情形）。
3. **亚像素相位不变式**（落位色）：`min(frac(rect.left × dpr), 1 − frac(...)) ≤ 0.05`（纵向同理）。不满足 → 整张位图被双线性插值平移，位图分辨率与比例都正确但笔画发灰——居中留白为小数时必然发生（例：容器 1266、页宽 589.6 → 左偏 338.2 × 1.25 = 422.75）。

前两条都成立而仍发虚时，归因按序排查：第 3 条（亚像素相位）优先于"合成层栅格未重建"（后者由 `SHARPNESS_FIX.layerRebuild` 兜底）。首轮实测（见 §13.4）已确认前两条成立且祖先链干净，当前主要嫌疑即为第 3 条。

### 4.2 渲染尺寸像素对齐算法

```ts
// src/services/renderGeometry.ts
export interface RenderTarget {
  targetWidth?: number
  targetHeight?: number
}

/** 目标 CSS 盒：适宽精确等于 targetWidth、适高精确等于 targetHeight，缺省 1:1（original 档） */
function fitCssSize(naturalWidth: number, naturalHeight: number, t: RenderTarget) {
  let scale = 1
  if (t.targetWidth) scale = t.targetWidth / naturalWidth
  else if (t.targetHeight) scale = t.targetHeight / naturalHeight
  return { width: naturalWidth * scale, height: naturalHeight * scale }
}

/** 像素对齐：以整数后备像素为基准反推 CSS，使 pixel/css/dpr 严格为 1 */
export function fitRenderBox(
  naturalWidth: number,
  naturalHeight: number,
  target: RenderTarget,
  dpr: number
): { cssWidth: number; cssHeight: number; pixelWidth: number; pixelHeight: number } {
  const d = dpr > 0 ? dpr : 1
  const css = fitCssSize(naturalWidth, naturalHeight, target)
  const pixelWidth = Math.max(1, Math.round(css.width * d))
  const pixelHeight = Math.max(1, Math.round(css.height * d))
  // 反推：CSS 尺寸不再独立取整，永远由整数像素除以 dpr 得到
  return { cssWidth: pixelWidth / d, cssHeight: pixelHeight / d, pixelWidth, pixelHeight }
}
```

`pdf.ts` 侧的接法（保持"以像素为唯一基准"；落地在私有函数 `resolveCanvasSize`，`SHARPNESS_FIX.pixelAlign` 关闭时走旧口径以便二分）：

```ts
const dpr = currentDpr()
const size = resolveCanvasSize(baseViewport.width, baseViewport.height, options, dpr)
const viewport = page.getViewport({ scale: size.pixelWidth / baseViewport.width }) // width 为整数
canvas.width = size.pixelWidth
canvas.height = Math.round(viewport.height) // 与 pixelHeight 同源推导，差 <1px
canvas.style.width = `${size.cssWidth}px` // 不能写 canvas.width / dpr：开关关闭时两分支口径不等价
canvas.style.height = `${canvas.height / dpr}px`
```

`imagePage.ts` 的 `computeImagePageSize` 保留导出与签名，内部改为委托 `fitRenderBox`，使两种格式的 CSS/像素口径完全同源。

### 4.3 诊断采样与判定

```ts
// src/services/sharpnessProbe.ts
export type SharpnessVerdict =
  | 'sharp'              // 两条不变式均成立，且无残留栅格疑点
  | 'no-canvas'          // 图片型 EPUB / 尚未渲染
  | 'canvas-resample'    // 位图不变式不成立：位图被重采样
  | 'page-scaled'        // 页面缩放不变式不成立：整层被浏览器缩放
  | 'container-mismatch' // 容器实测尺寸与渲染目标尺寸不一致
  | 'layer-suspect'      // 两条均成立但祖先链存在可疑合成样式（需人工看画面）

export function evaluateSharpness(input: SharpnessInput): { verdict: SharpnessVerdict; detail: string }
```

判定优先级（短路返回，避免一条读数给多个结论）：

1. `|visualViewport.scale − 1| > 0.01` 或 `|visualViewport.width − innerWidth| > 1` → `page-scaled`（**第一优先**：整层被缩放时位图比例仍可能是 1，先判 canvas 会得出错误结论）；
2. 无用 canvas（`width === 0` 或未挂载）→ `no-canvas`（EPUB 文字流走这条，但仍先过第 1 步）；
3. 任一 canvas 的 `|canvas.width / rect.width / dpr − 1| > 0.005` → `canvas-resample`；
4. 适宽/适高档下 `|container.clientWidth − 渲染目标宽| > 1`（双页按页拆分后比对）→ `container-mismatch`；
5. 任一 canvas 的 `max(offsetX, offsetY) > 0.05`（显示起点到最近整设备像素的偏差，单位设备像素）→ `subpixel-offset`；
6. 祖先链（`page-area` → … → `body`）存在 `transform ≠ none` / `filter ≠ none` / `will-change` 含 `transform|filter` / `backdrop-filter ≠ none` / `zoom ≠ 1` → `layer-suspect`；
7. 否则 `sharp`。

采样输出（单行结论 + 明细，整段 ≤1500 字符，避免被 `log:write` 的 2000 字符截断）：

```
[sharpness] verdict=page-scaled full=0 z=fitHeight dpr=1.25
  vv=scale:0.712 w:2691 h:1518 inner=1916x1082
  area=1916x1082 canvas=i0 1916x1082 css=1916x1082 ratio=1.000
  align=i0 snap=0.20,0.10 css fix=translate(0.20px,0.10px)
```

### 4.4 边界场景防护表

| 边界场景 | 现象 | 防护 |
|----------|------|------|
| dpr 为小数（1.25 / 1.5） | 后备像素取整后比例偏 0.1%~0.3% | §4.2 正向像素对齐；dpr 原值参与计算，不做 `round(dpr)` |
| 容器尺寸带小数（1279.5） | `clientWidth` 取整与 CSS 盒差 <1px | 渲染目标与显示尺寸都用 `clientWidth` 同一整数源，不混用 `getBoundingClientRect().width` |
| 全屏切换瞬间采样 | 读到旧尺寸，结论误判 | 采样入口统一 `doubleRaf` 后再读；全屏切换后的自动采样再加 80ms 延时 |
| 双页模式 | 两页各占一半宽，单页 ratio 正常但整体溢出 | 判定第 4 步按 `mode === 'double'` 用 `targetWidth * 2` 比对，避免误报 |
| canvas 尚未渲染（`width === 0`） | 除法得 `Infinity` | `no-canvas` 短路，不参与比例判定 |
| 纵向滚动（`VerticalScrollView`） | 无显示 canvas，只有行内多张位图 | 判定遍历行内 canvas，容器取滚动容器；缺 canvas 时降级为 `no-canvas` 但保留容器读数 |
| 系统缩放运行中变化 | `resize` 不必然触发 | `matchMedia('(resolution)` 一次性监听，命中后重挂并按新 dpr 重渲 |
| 居中留白为小数（`margin: auto`） | 位图比例 1.000 但整页笔画发灰（第二轮实测命中 `dx=0.50`） | 诊断报 `subpixel-offset` 作为位置读数；**不再做 translate3d 补偿**——像素级比对证明 Chromium 已自动对齐，补偿反而推离设备像素网格导致重采样（§13.5） |
| 打包版无 devtools | 用户无法取证 | 采样走 `log:write` 写主进程日志文件 |

### 7.1 新增 `src/services/renderGeometry.ts`（纯函数，可单测）

## 十二、风险与取舍记录

| 项 | 取舍 | 影响与备注 |
|----|------|------------|
| `page-scaled` 根因未能在静态代码中复现 | 先做诊断再定策略，同时把三类修复都落地（幂等、成本低） | 若实测为 `page-scaled`，`setZoomFactor(1)` + `setVisualZoomLevelLimits(1,1)` 是最直接杠杆；若为 `layer-suspect`，则以 `SHARPNESS_FIX.layerRebuild`（一帧 `will-change: transform` → 移除）兜底；两者都需要 M4 |
| `webContents.invalidate()` 的语义 | 采纳为兜底 | 文档主用途是 offscreen 渲染，对普通窗口属"请求重绘"的宽松保证；因此不把画面清晰度**唯一**寄托于它，必须与层重建、重渲并存 |
| 像素对齐会改变 canvas 的 CSS 尺寸（±0.5px） | 接受 | 翻页快照/卷曲本就按 `getBoundingClientRect` 实际显示矩形合成（见既有 pageCurl 口径），不依赖预设 style 值；但 `imagePage.test.ts` 的断言需同步 |
| `cacheSignature` 升 v3 | 接受 | 首次打开旧书会全量重渲一次（原本换视口也要重渲），内存占用不变 |
| 采样快捷键面向生产 | 接受 | `Ctrl+Alt+Shift+D` 与 `EpubReaderView` 的 `Ctrl+Shift+D`、AI 选词的 Esc/A 均不冲突；采样为纯读操作，无副作用 |
| 超采样（2x）延后 | 接受 | 位图分辨率不足属"清晰但不细腻"，与"发虚"是不同观感；先修错位再谈细腻度，避免用 2x 内存掩盖几何缺陷 |
| macOS 未验证 | 记录风险 | `titleBarStyle: 'hidden'` 下全屏与窗口尺寸链路不同，`page-area` 高度可能受红绿灯避让影响；`renderTargetSize` 用容器实测（而非 `window.inner*`）恰好对此更稳健，但仍需 mac 环境回归 |
| 层重建可能引起一帧闪烁 | 有限接受 | 只在全屏切换后触发一次，且在用户已感知画面变化的时刻；若实测有闪，退化为只依赖 M4 主进程复位 |

   - `mad ≈ 0` 且 `edge ≈ 1` → 屏幕输出与 canvas 位图逐像素一致，说明上屏阶段没有重采样，发虚来自位图本身（下一步：超采样 / 改 canvas 背景透明以启用 LCD 子像素抗锯齿）。
   - `now` 的 `edge` 明显小于 1，而 `noSnap`/`noScroll`/`bare` 中某一项回到 1 → 直接定位到那一项关掉的内容就是降质根因。
   - 所有变体 `edge` 都低 → 降质在已对照项之外的合成环节，继续扩展变体。
6. 打包产物重复第 1 步，确认日志文件出现 `[renderer] [sharpness] …`（生产可取证）。

### 13.5 亚像素吸附（已证伪并默认关闭）

- **目标**：让页面组的显示起点落在整设备像素（`left × dpr ∈ ℤ`），消除整张位图的插值平移。
- **实现**：`devicePixelSnapOffset(left, top, dpr)` 算补偿量（`round(left×dpr)/dpr − left`，纯函数可单测）；`snapToDevicePixel(el)` 用 `translate3d(x, y, 0)` 施加，并用 `WeakMap` 记录已施加量。
- **证伪（2026-11-20）**：`[sharpness-pixel]` 比对显示，开启吸附时 `now edge=0.79`（屏幕被重采样），而关掉 transform 的 `noSnap` / `noScroll` / `bare` 三个变体全部 `edge=1.00`、`mad=0.00`（逐像素一致）。
  - 根因：Chromium 对 canvas 的显示原点本来就会做设备像素对齐；`getBoundingClientRect()` 读到的 0.25 设备像素只是 CSS 布局浮点，真正上屏时已被取整。
  - 强行 `translate3d` 补偿反而把 canvas 推离整数设备像素网格，触发双线性插值 → 整页发虚。
- **结论**：亚像素偏移的**诊断读数**仍保留（它真实反映了布局位置），但不再作为需要修复的缺陷；`SHARPNESS_FIX.snapDevicePixel` 已删除，`snapToDevicePixel()` 函数已从 `renderGeometry.ts` 移除，[`ReaderView.vue`](file:///d:/ai_work/ireader/src/views/ReaderView.vue) 不再调用。
- **已尝试但未证实的作用域**：
  - 移除 `.page-wrap canvas` 的 `canvas-in` opacity 淡入 → 用户反馈仍模糊，已恢复。
  - 给 `.page-content` 加 `will-change: transform` → 用户反馈仍模糊，已移除。
- **验证**：`renderGeometry.test.ts` 函数单测保留；全量单测通过。

### 13.6 像素级比对（新增，2026-11-19）

几何不变式只能证明「位图尺寸、页面缩放、亚像素相位」合格，证明不了上屏那一步有没有被合成器重采样。用户前两轮实测均显示 `ratio=1.000` / `snap=0.00` / `ancestors=-`，但画面仍模糊，因此新增屏幕像素与 canvas 后备位图的逐像素比对。

- **实现**：`src/services/pixelProbe.ts`。
  - `runPixelProbe(canvas, variants)` 用既有 `window:captureRegion` IPC 取页面中部可见区域，再按同一矩形从 canvas 后备位图裁切；两者做亮度 MAD + 边缘能量比对，并搜索 ±3 设备像素的整数对齐。
  - `compareScreenToBacking()` 为纯函数，已覆盖：逐像素一致、整像素错位、半像素插值平移、空白区域、透明像素按黑底合成、尺寸约束不满足。
  - `styleVariant()` 给对照变体施加临时 `!important` 内联样式，每项变体多关掉一处可能让上屏重采样的环节：
    1. `now`：当前状态（无吸附 transform；历史版本含 `snapToDevicePixel`，已移除）。
    2. `noSnap`：强制 `transform: none`，排除吸附 transform 本身引入的合成层错位。
    3. `noScroll`：`transform: none` + `.page-area` `overflow: hidden`，排除滚动容器合成层。
    4. `bare`：以上 + 隐藏 `.ai-layer` 与 `.hotzone` 覆盖层，排除覆盖层 filter/backdrop-filter。
- **触发**：`ReaderView.sampleSharpnessNow()` 在旧 `[sharpness]` 采样之后自动执行，面板先收起（避免自身遮住页面），完成后与几何读数一起展示 30 秒。
- **判读**：
  - `mad < 1` 且 `edgeRatio > 0.97` → 屏幕输出与位图逐像素一致，发虚来自位图本身。
  - `now` 的 `edgeRatio` 低，但 `noSnap` / `noScroll` / `bare` 之一回到一致 → 直接定位根因。
  - 所有变体都低 → 根因未在本次对照项内。
- **验证**：`pixelProbe.test.ts` 新增 11 例；`npm test` 35 文件全绿；`npx vite build` 成功。
