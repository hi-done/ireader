# 合集创建时间字段映射修复设计方案

> 状态：已实现（M1~M3 完成：`npm run typecheck` / `npm test` 通过，手工冒烟已验证）
> 目标版本：v1.4.2（版本号沿用当前 package.json，具体发版由用户决定）
> 范围：修正 `collection:create` / `collection:list` / `collection:rename` 返回的合集对象字段形状（`created_at` → `createdAt`），修复合集「按添加时间」排序失效
> 实现约束：遵循 `ireader-dev-tasks`（任务 A）与 `ireader-code-conventions`（DB snake_case ↔ TS camelCase 在 repo 层手动映射、Result 契约、中文注释）

## 一、需求拆解与验收标准

| # | 原始需求 | 设计落点 | 验收方式 |
|---|----------|----------|----------|
| 1 | 修复合集「按添加时间」排序无效 | `collectionsRepo` 新增纯映射 `toCollection(row)`；handlers 的 `collection:create` / `list` / `rename` 返回 `Collection`（camelCase） | 主页排序切「添加时间」，升序与降序的合集顺序互为逆序 |
| 2 | 新建合集后排序位置正确 | `createCollection` 拿到的对象带真实 `createdAt` | 新建合集后（排序=添加时间 降序）新合集排在合集区最前；升序排在最后 |
| 3 | 不破坏既有行为 | 渲染层与 `preload.ts` 均零改动，仅主进程返回值形状修正 | 重命名、解散、移入/移出、合集卡封面与数量均与修复前一致 |

**核心验收口径**：存在 ≥2 个创建时间不同的合集时，主页排序切「添加时间」并切换升/降序，合集卡片顺序在两种方向下互为逆序（修复前升序无任何变化）。

## 二、非目标（本期不做）

- 不改渲染层排序实现：`src/services/libraryList.ts` 的 `sortCollections` 继续读 `createdAt`，不做 `createdAt ?? created_at` 双字段兜底（已与用户确认，避免掩盖上游遗漏）。
- 不新增单测：受影响逻辑位于主进程边界（`collectionsRepo` 依赖 better-sqlite3 原生模块，无法在 Vitest 中导入），改以 typecheck + 手工冒烟验收。
- 不改 DB schema、不加迁移：`collections.created_at` 已存在，属纯返回形状修正。
- 不排查其它域：已核实 `library:list` 经 `libraryService.rowToBook`、`settings:all` 经 `settingsRepo.getAll`、`stats:summary` 经 `statsService.summary` 均已映射；本问题只存在于合集域。

## 三、总体设计

### 3.1 分层与数据流（修复点）

```
┌─ 渲染层（零改动） ────────────────────────────────────────────┐
│ libraryList.sortCollections：读 c.createdAt 作为「添加时间」键 │
│ library store：collections: Collection[]                      │
└───────────────────────────▲───────────────────────────────────┘
                            │ 修复前：{ id, title, created_at } ← 字段名不符，createdAt = undefined
                            │ 修复后：{ id, title, createdAt }
┌─ 主进程 ──────────────────┴───────────────────────────────────┐
│ handlers.ts                                                   │
│   collection:create → toCollection(collectionsRepo.create(...))│
│   collection:list   → collectionsRepo.list().map(toCollection) │
│   collection:rename → toCollection(collectionsRepo.rename(...))│
│                       ▲ 新增纯映射（snake_case → camelCase）   │
│ collectionsRepo：仍返回 CollectionRow（DB 形状，repo 层不改语义）│
│                       ▼                                       │
│ SQLite collections（id, title, created_at）— 无迁移            │
└───────────────────────────────────────────────────────────────┘
```

### 3.2 关键决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 修复位置 | 主进程 handler 边界，repo 导出纯映射 `toCollection` | 与既有 `progressRepo.toReadingProgress`、`libraryService.rowToBook` 同构：DB 形状止于主进程，IPC 只传 `shared/types.ts` 的模型；渲染层无需认知 `created_at` |
| repo 返回值 | `collectionsRepo` 方法仍返回 `CollectionRow` | repo 承担「SQL + DB 形状」，映射放在导出函数里，不改变 repo 既有调用语义，改动面最小 |
| 三处通道一起修 | create / list / rename 全部映射 | 三者返回同构对象；只修 list 会让新建合集立刻失去 `createdAt`（store `createCollection` 直接入列），修复不完整 |
| 排序侧兜底 | 不加 | 用户已确认只修边界；加了兜底会让「漏映射」再次静默降级为 0，掩盖根因 |
| 单测 | 不新增 | `collectionsRepo` 依赖 `better-sqlite3`（Electron ABI），Vitest 下无法导入；映射与 SQL 一并由冒烟覆盖（与项目「只测纯逻辑」约定一致） |

## 四、问题成因与影响口径

### 4.1 成因

`electron/db/repos/collectionsRepo.ts` 直接返回 `SELECT *` 的行对象（字段 `created_at`），而 `preload.ts` / `src/services/ipc.ts` 声明返回 `Collection`（字段 `createdAt`）。`wrap()` 只做 `Result` 包装、不做字段映射，于是 `created_at` 原样穿过 IPC。

`sortCollections` 里 `addedAt: a.createdAt` 取到 `undefined`：

```ts
compareItems({ addedAt: undefined, ... }, { addedAt: undefined, ... }, 'addedAt', dir, locale)
// → (undefined - undefined) * dir = NaN
```

`Array.prototype.sort` 对比较函数返回 `NaN` 的处理等价于 `0`，因此合集顺序原样保留 SQL 的 `ORDER BY created_at DESC`——表现为「按添加时间」升降序切换对合集无效。

### 4.2 影响面（已核实）

| 消费点 | 影响 |
|--------|------|
| `sortCollections`（`src/services/libraryList.ts` L91-92） | 「添加时间」排序对合集完全失效（唯一实际用户可见的功能缺陷） |
| `store.createCollection`（`src/stores/library.ts` L82-86） | 新建合集对象缺 `createdAt`，即使 list 修好，新建后仍会丢排序键 |
| `store.renameCollection` | 已按本仓库上一方案只 patch `title`，不受影响（修复后语义安全） |
| `CollectionCard` / `LibraryManageView` | 只读 `id` / `title`，无影响 |

### 4.3 边界防护

| 场景 | 处理 |
|------|------|
| 合集被别处解散后 rename | 既有 `INVALID_PARAMS` 分支不变，本方案不动 |
| `created_at` 为 0 或异常值 | 映射原样透传，不做校正；排序行为与书一致（按数值大小） |
| 旧数据库数据 | 无迁移需求，`created_at` 自 v2 迁移起即非空 |

## 五、数据模型

无 schema 变更。`collections` 表保持 v2 迁移定义：

```sql
CREATE TABLE IF NOT EXISTS collections (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  title      TEXT    NOT NULL,
  created_at INTEGER NOT NULL
);
```

`collectionsRepo` 新增导出映射（接口签名不变，仅新增导出）：

```ts
/** DB 行 → 渲染层模型（snake_case → camelCase）；与 progressRepo.toReadingProgress 同构 */
export function toCollection(row: CollectionRow): Collection {
  return { id: row.id, title: row.title, createdAt: row.created_at }
}
```

需在文件头补充 `import type { Collection } from '../../../shared/types'`（与 `progressRepo.ts` 相同的相对路径写法）。

## 六、IPC 契约

无新增通道、无新增类型、无 ErrorCode 变更。仅修正既有三个通道的**实际返回形状**，使其与既有声明一致：

| 通道 | 入参 | 返回（声明值，修复后与实际一致） | 说明 |
|------|------|----------------------------------|------|
| `collection:create` | `title: string` | `Result<Collection>` | `{ id, title, createdAt }` |
| `collection:list` | — | `Result<Collection[]>` | 同上，`ORDER BY created_at DESC` |
| `collection:rename` | `{ id, title }` | `Result<Collection>` | 同上 |

`Collection` 定义保持不变（`shared/types.ts` L52-56）：`id` / `title` / `createdAt`。

## 七、主进程实现

- `electron/db/repos/collectionsRepo.ts`：新增 `toCollection` 导出（见 §5）；`create` / `list` / `rename` 的 SQL 与返回类型不变。
- `electron/ipc/handlers.ts`：import 补 `toCollection`，三处返回值改为映射后对象——

  ```ts
  import { collectionsRepo, toCollection } from '../db/repos/collectionsRepo'

  ipcMain.handle('collection:create', wrap((title: string) => {
    const trimmed = title.trim()
    if (!trimmed) throw { code: 'INVALID_PARAMS', message: '合集名不能为空' }
    return toCollection(collectionsRepo.create(trimmed, Date.now()))
  }))

  ipcMain.handle('collection:list', wrap(() => collectionsRepo.list().map(toCollection)))
  ```

  `collection:rename` 内 `return toCollection(updated)`。handler 仍只做「校验 + 编排」，映射本身在 repo 层。
- `electron/preload.ts`、`src/services/ipc.ts`、store、视图：**不改动**（声明本就是正确的）。

## 八、渲染层实现

不改动。要点说明：

- `sortCollections` 已按 `createdAt` 读取（`src/services/libraryList.ts` L91-92），修复后自动生效，无需改排序逻辑。
- `store.createCollection` 直接 `[created, ...collections.value]`，修复后对象自带 `createdAt`，排序与显示一致。
- `store.renameCollection` 只 patch `title`，字段结构不变。

## 九、页面 / 交互设计

无 UI 变更。用户可见变化仅一处：主页排序下拉选「添加时间」时，合集卡片顺序随升/降序真实变化（修复前两方向表现相同）。

### 11.1 单元测试

不新增用例（理由见 §3.2）。现有相关用例保持通过，作为「排序纯函数未被改坏」的回归：

### 11.2 手工冒烟清单（`npm run dev`）

前置：库里存在 ≥3 个创建时间不同的合集（不足就先新建两个再重启，确保 `created_at` 有差异）。

1. `npm run typecheck` —— 零错误（重点：三处 handler 返回类型与 preload 声明一致）。
2. `npm test` —— 全部通过。
3. 主页排序选「添加时间 · 降序」→ 合集区从上到下为「最新创建 → 最早创建」。
4. 切「添加时间 · 升序」→ 合集顺序正好反向（**这是修复前的失败点**）。
5. 保持升序时新建一个合集 → 新合集出现在合集区最后（最新创建排在升序末尾）；切降序后回到最前。
6. 重命名任一合集 → 名称更新且排序位置不变；解散任一合集 → 其余合集排序正常。
7. 重启应用 → 合集排序仍正确（`created_at` 持久化无变化）。

## 十三、风险与取舍记录

| 项 | 取舍 | 影响与备注 |
|----|------|------------|
| 只修边界不兜底 | 排序侧不写 `createdAt ?? 0` | 未来若再出现漏映射，会再次表现为「排序静默失效」而非静默按 0 排序；根因更易定位，代价是需要人工冒烟发现 |
| 无自动化回归 | 不新增测试 | 主进程 repo 依赖原生模块，Vitest 无法导入；可扩展点：将来若把 row→model 映射抽成不依赖 DB 的纯模块（如 `electron/db/mappers.ts`），即可为其补单测 |
| 语义不变 | `collectionsRepo` 仍返回 DB 行 | 保持 repo 层单一职责；若后续 repo 需被多处消费，可再考虑让 repo 直接返回模型（届时同步改 `rename` 的 `undefined` 分支语义） |
| 关联文档 | 本方案是《合集页头重命名按钮设计方案-20261101.md》§13「风险与取舍记录」中 `created_at` ↔ `createdAt` 风险项的根因修复 | 两文档互不覆盖：前者交付重命名功能并规避副作用，本文档消除根因 |
