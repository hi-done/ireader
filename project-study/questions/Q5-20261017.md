# Q5-20261017 EPUB 阅读器缩放为何采用百分比而非适宽/适高/原始

## 问题

为什么 EPUB 阅读界面的缩放是 50%、100%、200% 这类百分数，而不像 PDF 那样提供「适高 / 适宽 / 原始」？

## 回答

**结论：百分比与 PDF 三档模式描述的不是同一件事。** PDF 是“定尺寸页面 + Canvas 位图”，三档模式回答的是“这张固定尺寸的纸怎么放进视口”；EPUB 则没有统一的固有页面像素尺寸——文字型书是 HTML/CSS 文档流（百分比是**字号**），图片型书是把图片按 contain 适配进视口（百分比是**相对适配结果的倍率**）。再加上 EPUB 渲染在 iframe 内、没有 PDF 那样的滚动/拖拽平移承接，固定“适宽/适高”会裁掉另一边，因此没有引入 PDF 那套模式。

### 一、PDF 三档模式成立的前提：页面尺寸固定，且有平移兜底

- pdf.js 每页都有一个确定的原始视口：`page.getViewport({ scale: 1 })`（`src/services/pdf.ts` L93-98）。三档模式只是把这个固定尺寸映射成不同的渲染目标（`src/views/ReaderView.vue` L391-409）：
  - `fitWidth` → `targetWidth = 视口宽`（双页取半宽）；
  - `fitHeight` → `targetHeight = 视口高`；
  - `original` → 不传目标尺寸，pdf.js 按 `scale = 1` 原尺寸绘制；
  - `custom` → 以适高为基准乘倍率。
- 尺寸超出视口时，`.page-area` 是 `overflow: auto`（`ReaderView.vue` L829-837），并带拖拽平移（L620-631）。所以“适宽”可以放心地让高度溢出，“原始”也可以比屏幕大——用户能滚/拖着看。

### 二、EPUB 其实是两种布局，共用“百分比”外观

顶栏同一个下拉框按检测出的布局分流（`src/views/EpubReaderView.vue` L29-47、L487-500）；布局由 `detectImageBasedBook()` 判定（`src/services/epub.ts` L95-114）。

**1. 文字型书（reflowable）——下拉框控制的是字号，不是页面缩放**

- 内容是 HTML/CSS，由 epub.js 在 iframe 里按 CFI 分页；正文列宽始终等于 iframe 视口宽，也就是说“适宽”本来就是它的固有排版方式，不是一个可切换的模式。
- HTML 没有“原始像素尺寸”的概念，`original` 无从定义；而“适高”也只能靠改字号/分页去凑，本质仍是字号问题。
- 因此这里调用的是 `rendition.themes.fontSize(`${fontSize}%`)`（`epub.ts` L118-134；`src/stores/epubReader.ts` L293-300），档位为 80%~200% 的字号百分比。

**2. 图片型书（pre-paginated）——百分比是相对“整页适合视口”的倍率**

- 每页是一张 img/svg，确实有固有尺寸；项目自实现了 `fitPrePaginatedContents()`（`epub.ts` L149-224），核心公式（L182-185）为：

  `scale = min(视口宽 / 图固有宽, 视口高 / 图固有高) × (zoomPercent / 100)`

- 也就是 **100% 的定义是“整页 contain 适配视口”**，不是“图片原始尺寸”。透视到具体页面：竖长页自动变成“适高”，横宽页自动变成“适宽”；`zoom` 只在这个适配结果上做 50%~300% 的放大/缩小（`epubReader.ts` L306-314），档位为 50/75/100/125/150/200（`EpubReaderView.vue` L490），Ctrl+滚轮/快捷键以 10% 步进（L632-644、L715-730）。
- 每次 `rendered` 后都会按当前 `getZoom()` 全量重适配（`epub.ts` L254-268、L270-337），所以切单双页、翻页、改缩放都会以新视口重新计算。

### 三、为什么图片型 EPUB 也不做“适宽/适高/原始”

1. **页面纵横比不统一，contain 才是安全默认值。** 一本书里页面比例可能各不相同，固定“适宽”必然裁掉某些页的底部，固定“适高”必然裁掉某些页的左右；`min(宽比, 高比)` 才能保证每页完整可见。PDF 虽然页面尺寸也可能不同，但它有滚动/平移兜底，裁切问题不成立。
2. **EPUB 没有平移承接。** `fitPrePaginatedContents()` 把 iframe 内 `body` 设为 `overflow: hidden`（`epub.ts` L198），`EpubReaderView` 也没有任何平移/滚动逻辑。超出视口就是中心裁切。此时“适宽/适高”会暗示“另一边完整可见”，与实际行为不符；百分比则更诚实地表达“以中心为锚点放大/缩小”。
3. **单页/双页/封面的适配基准不唯一。** `installPrePaginatedFit()` 要处理双页半屏、封面单独成页撑满整屏、双页贴中线对齐、prev 翻页 prepend 后全量重对齐等（`epub.ts` L226-353）。如果引入“适宽”，还要分别定义“半屏宽的适宽”和“整屏宽的适宽”；百分比是一个纯乘数，天然适配所有这些场景，不必为每种布局再定一套基准。
4. **“原始”在 EPUB 里没有稳定定义。** 图片可能有 2000px 宽，1:1 在 1080p 视口会严重溢出且无法平移；而且 pre-paginated 页面的 CSS 视口可能与图片像素并不一致，所谓“原始”到底指图片像素还是 XHTML 视口尺寸，本身就有歧义。
5. **进度持久化复用了 PDF 的 zoom 结构。** `ReadingProgress.zoom` 是 `{ mode, scale }`（`shared/types.ts` L19）。EPUB 保存时把百分比塞进 `scale`，并把 100% 映射为 `'fitHeight'`、其余映射为 `'custom'`（`epubReader.ts` L325-342）；恢复时只读 `scale`，忽略 `mode`（L107-108）。这只是存储兼容，**不代表 EPUB 真的支持“适高”模式**。若引入真正的三档模式，就必须区分“contain 100%”与“真正的适高”，还要在恢复时按布局解释 mode，歧义和迁移成本都更高。
6. **历史原因。** 项目文档记录了这条设计的由来：漫画书 section 没有 `<meta viewport>`，epub.js 官方 `fit()` 解析出 NaN 而失效，`themes.fontSize()` 又对图片无效，于是自实现 contain 缩放，并把顶栏下拉框按布局分流为 50%~200% 的缩放档位（`specs/EPUB阅读支持问题与解决方案.md` L23）。

### 四、两种“100%”的语义差异（最容易误解的点）

| 维度 | PDF | EPUB 文字型 | EPUB 图片型 |
|---|---|---|---|
| “页面”是什么 | 固定尺寸页面 | HTML/CSS 文档流 | 每节一张图 |
| 100% 的含义 | 原始页面 1:1（`original`） | 默认字号 | 整页 contain 适配视口 |
| 适宽 | 独立模式 | 固有排版方式（列宽=视口宽） | 由页面比例自动触发 |
| 适高 | 独立模式 | 只能通过字号/分页间接实现 | 由页面比例自动触发 |
| 原始 | 独立模式 | 无定义 | 无稳定定义 |
| 溢出处理 | 滚动 + 拖拽平移 | 重新分页 | 中心裁切（无平移） |

所以 EPUB 的百分比**不是“相对原始尺寸”**，而是“相对整页适配结果的倍率”；文字型书的百分比更是字号，与页面几何缩放无关。

### 五、如果要改成 PDF 式模式，需要做什么（推断与建议）

> 以下为基于现状的改造推断，不是当前代码行为。

- 只有图片型书（pre-paginated）适合增加“适宽/适高/原始”；文字型书无法稳定定义 `original`，`fitHeight` 也只能退化为字号/分页策略。
- 需要：给 EPUB 单独的缩放模式状态；让 `fitPrePaginatedContents()` 接收模式并计算 `scale`（适宽 = 视口宽/图宽，适高 = 视口高/图高，原始 = 1）；为超出视口的情况补平移/滚动；扩展进度存储以区分“contain 100%”与真正的 fit 模式；最后还要处理单页/双页/封面的基准差异。
- 收益主要是与 PDF 交互一致；代价是 EPUB 侧多一套布局分支和交互兜底。若只想要“完整显示”，现有的 100%（contain）已经覆盖；若想放大细看，百分比 + 中心裁切在当前无平移的实现下更简单。
