# Q8-20261106 GitHub CI 生成 Release 后把产物再上传到自建服务器

## 问题

能否在 GitHub Actions 的 CI/Release 流程生成 Release 之后，把 Release 产物再发送到自建服务器 `http://112.23.1.101:8080/upload`？应改哪份 workflow、怎么配置？

## 回答

### 结论

可以，而且当前工作流里已经存在一个天然的接入点：`release.yml` 的 `publish` 任务会把 macOS / Windows 两个平台的产物统一下载到 `artifacts/` 目录，再一次性发布到 GitHub Release。在这个位置（或紧随其后的一个独立任务里）增加一个上传步骤，即可把同一批文件推送到自建服务器。

`ci.yml` **不需要改动**：它只跑类型检查与单元测试，不产出任何打包文件（`.github/workflows/ci.yml:24-29`），所以与「上传发布产物」无关。

### 现状事实（来自代码）

1. **触发条件不同**：`ci.yml` 在 `push: [main]` 与 `pull_request` 时跑（L3-6）；`release.yml` 只在推送 `v*` 标签时跑（L3-6）。
2. **三段式发布**：`release.yml` 为 `test`（L12-30）→ `build`（L32-124，OS 矩阵 macOS/Windows）→ `publish`（L128-160）。`build` 明确**不**依赖 `test`（L33-36 的注释解释了这是为了和 macOS runner 排队时间重叠），测试是否通过由 `publish` 的 `needs: [test, build]` 兜住。
3. **`build` 里上传的 artifact 精确清单**：
   - macOS：`release/*/*.dmg`、`release/*/latest-mac.yml`（L103-105）
   - Windows：`release/*/IReader-*-win.exe`、`IReader-*-win.exe.blockmap`、`latest.yml`（L118-121）
   - 两者都使用 `compression-level: 0`、`retention-days: 1`（L108-109 / L123-124）。
4. **`publish` 的产物形状**：`download-artifact@v8` 带 `merge-multiple: true` 下载到 `artifacts/`（L132-137），因为 `build` 里的通配符第一层就是版本目录，所以实际是 `artifacts/<version>/IReader-<version>-mac.dmg` 这种带版本子目录的形状——L142-147 的注释记录了 v1.4.0 曾因误写成平铺 glob 而「Release 零产物却全绿」的事故，可作上传步骤写 glob 时的前车之鉴。
5. **文件名由构建配置决定**：`package.json:72`（mac `IReader-${version}-mac.${ext}`）、`package.json:81`（win `IReader-${version}-win.${ext}`），输出目录为 `release/${version}`（`package.json:55`）。
6. **上传服务器与「应用内更新」是两条独立链路**：`package.json:48-52` 的 `build.publish` 是 `provider: github`（owner `hi-done` / repo `ireader`），`electron/services/updaterService.ts:19` 的 `RELEASES_BASE` 也指向 GitHub Releases。把产物额外上传到自有服务器，只是多一份分发/备份副本，**不会**改变应用内检查更新与差量下载的走向。

### 方案取舍

- **推荐：新增独立任务 `upload-server`，`needs: publish`**，在该任务内重新 `download-artifact` 再推送。
  - 好处：与发版结论解耦——GitHub Release 已经 published 后，服务器连不上或上传失败，只是这个附加任务变红，不会让「发版」这件事看起来失败；同时也符合现有「发布只在一个任务里做一次」的收口思路。
- **次选：把上传步骤直接塞进 `publish` 任务里 `action-gh-release` 之后**。省一次 artifact 下载，但上传失败会让整个 `publish` job 失败，与「Release 已成功创建」的事实相矛盾。
- **不推荐：在两个 `build` 矩阵任务里各自上传**。这会破坏 L90-93 与 L126-127 注释里已经确立的「矩阵任务各自发布会产生半成品」的教训（v1.3.0 实测：Windows 先 published、dmg 还没到），两个平台并发往同一接口推同名文件也存在互相覆盖的风险。

### 落地配置（示例，需按服务器接口微调）

先向服务器方确认三件事，再决定 curl 的形态：

1. 接收方式：`POST` multipart（字段名，例如 `file`）／`PUT` 原始流／自定义 JSON+base64；
2. 是否需要鉴权（Bearer token / 自定义 header / 签名）；
3. 是否要求保留版本子目录、同名文件是否允许覆盖。

若为最常见的 multipart POST（注意用户原话里的 `/uplaod` 应为 `/upload`，路径以服务器实际路由为准）：

```yaml
  upload-server:
    # 服务器分发与 GitHub Release 解耦：Release 已发布后，这里失败不影响发版结论
    needs: publish
    runs-on: ubuntu-latest
    steps:
      - name: 下载各平台产物
        uses: actions/download-artifact@v8
        with:
          pattern: release-*
          path: artifacts
          merge-multiple: true

      - name: 上传到自建服务器
        env:
          UPLOAD_URL: ${{ vars.UPLOAD_URL }}        # 例：http://112.23.1.101:8080/upload
          UPLOAD_TOKEN: ${{ secrets.UPLOAD_TOKEN }} # 服务器需要鉴权时使用
        shell: bash
        run: |
          set -euo pipefail
          shopt -s globstar nullglob
          for f in artifacts/**/*; do
            [ -f "$f" ] || continue
            echo "→ $f"
            curl -fsS -m 300 --retry 3 --retry-delay 5 \
              -H "Authorization: Bearer $UPLOAD_TOKEN" \
              -F "file=@${f}" \
              "$UPLOAD_URL"
          done
```

若服务器是「PUT 到 `/<文件名>`」形态，把 curl 换成 `curl -fsS -T "$f" "$UPLOAD_URL/$(basename "$f")"`；若要求保留版本子目录，用 `${f#artifacts/}` 作为远端路径。

要点说明：

- **不要硬编码地址与凭据**：地址放仓库 Variables（`vars.UPLOAD_URL`），凭据放 Secrets（`secrets.UPLOAD_TOKEN`）。GitHub 对 `secrets` 自动打码，写进 `run` 的明文 token 会留在公开日志里。
- **必带 `-f`**：否则 curl 在 4xx/5xx 时退出码仍为 0，会上演「全绿但文件没上去」的静默失败（与本仓库 gh-release 那次零匹配事故同一类坑）。
- **注意 artifact 保留期**：`retention-days: 1`（release.yml L109/L124），`upload-server` 必须紧跟 `publish` 执行；若隔天想「只重跑上传」，artifact 已被清理，需要重新打 tag 或改用 `gh release download` 从已发布的 Release 取文件。
- **注意出网与安全**：`112.23.1.101` 属公网段，但 GitHub 托管 runner 位于海外，8080 端口是否放行、链路是否稳定需实测（本地 `curl -I` 通过不等于 runner 通过）；走 `http://` 是明文传输，若服务器能开 HTTPS 建议改用 HTTPS。也可以考虑改成 `appleboy/scp-action` 之类经 SSH 推送，避开裸 HTTP 接口。
- **与更新功能的关系**：只有当 `package.json:48-52` 的 `publish.provider` 改成 `generic`（指向该服务器）并把 `latest.yml`、`latest-mac.yml` 与安装包放在同一可达目录时，「应用内检查更新」才会改走服务器；否则服务器上的副本仅作手动下载/归档，用户点「检查更新」仍读 GitHub Releases（`updaterService.ts:19`）。

## 相关代码

- `.github/workflows/ci.yml`（L1-29）：push main / PR 触发，仅安装依赖 + `typecheck` + `test`，无打包与产物，与上传无关
- `.github/workflows/release.yml`（L3-6）：`v*` 标签触发发版
- `.github/workflows/release.yml`（L32-124）：OS 矩阵构建，`npm run build -- --publish never` 后按平台上传 workflow artifact，是「产物清单」的唯一定义处
- `.github/workflows/release.yml`（L128-160）：`publish` 统一下载全部 artifact 并一次性 `action-gh-release`，是新增服务器上传步骤的正确落点（同目录 `artifacts/**`）
- `.github/workflows/release.yml`（L142-155）：注释记录 v1.4.0 「glob 零匹配但全绿」事故，是上传脚本必须 `set -e` / `curl -f` 的直接依据
- `package.json`（L45-56）：`build.directories.output` 与 `publish.provider: github`，决定产物路径与更新链路
- `package.json`（L64-82）：mac/win `artifactName`，决定上传到服务器的文件名
- `electron/services/updaterService.ts`（L19-23）：`RELEASES_BASE` 指向 GitHub Releases，Windows 才支持自动安装；说明额外上传服务器不影响更新链路
