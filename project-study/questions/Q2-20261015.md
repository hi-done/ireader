# Q2-20261015 中文文档 PDF 中文不显示的根因

## 问题

为什么文档类 PDF（如中文 LaTeX 排版书籍）在 IReader 中打开后中文全部不显示（英文与数字正常、页面版式还在），而 WPS 打开正常？

## 回答

结论先行：**IReader 的 pdf.js 没有配置 CMap 资源（`cMapUrl` / `cMapPacked`），导致这类 PDF 的中文字体在「字体翻译（translateFont）」阶段加载失败，整段中文不会被渲染**。这不是纯编码显示错误，pdf.js 控制台会明确报错，只是被 IReader 静默忽略了。

### 一、为什么这类 PDF 的渲染依赖 pdf.js 的「内置 CMap」

以测试书《初等数论 张毅超.pdf》（XeLaTeX + xdvipdfmx 生成）为例，解压其对象流得到的字体字典：

- 中文字体：`FandolSong / FandolHei / FandolKai` 的 **Type0 复合字体**（CIDFontType0C 子集嵌入），`/Encoding /Identity-H`、`/CIDSystemInfo << /Registry (Adobe) /Ordering (GB1) >>`，且**没有 `/ToUnicode`**；
- 英文字体：`SFRM1440 / LMRoman8-Regular` 等（Type1 或带 `/ToUnicode` 的复合字体）。

pdf.js 源码 `buildToUnicode()`（`pdf.worker.mjs` L32872-32912）中有一条分支（L32883）：

```
properties.composite && (
  properties.cMap.builtInCMap && !(properties.cMap instanceof IdentityCMap)
  || properties.cidSystemInfo?.registry === "Adobe"
     && (ordering === "GB1" || "CNS1" || "Japan1" || "Korea1")
)
```

即：对 `Identity-H` 编码、CIDSystemInfo 为 Adobe-GB1/CNS1/Japan1/Korea1 且**缺少 ToUnicode** 的复合字体，pdf.js **必须**加载内置 CMap `Adobe-GB1-UCS2`（`${registry}-${ordering}-UCS2`，L32888-32893），用它把 CID 映射为 Unicode，才能完成字体构建——这是渲染与文字提取的共同前置步骤（调用点见 translateFont 流程内 L32786）。

这个 CMap 不是代码，而是独立数据文件（`Adobe-GB1-UCS2.bcmap`，约 33 KB），属于 pdf.js 发行包中**需要宿主按需提供的资源**（`pdfjs-dist/cmaps/` 目录），由 `cMapUrl` 参数指定位置、`cMapPacked` 声明是否为二进制压缩格式。

### 二、IReader 缺失了什么（修复前状态，20261015 已修复，见第四节）

`src/services/pdf.ts`（L15-25）加载文档时只传了文档地址：

```
const task = pdfjsLib.getDocument({ url })   // 没有 cMapUrl / cMapPacked / standardFontDataUrl
```

于是 pdf.js 请求 `Adobe-GB1-UCS2` 时落到 `BaseCMapReaderFactory.fetch`（`pdf.mjs` L6040-6045），`baseUrl` 为空直接抛：

```
Ensure that the `cMapUrl` and `cMapPacked` API parameters are provided.
```

完整故障链：

```
getDocument({ url }) 缺 cMapUrl
  → worker 请求 Adobe-GB1-UCS2 内置 CMap
  → 主线程 DOMCMapReaderFactory 因 baseUrl 为空抛错
  → translateFont failed（pdf.worker.mjs L31163 打 warning 后静默跳过该字体）
  → 使用该字体的全部中文不渲染；英文/数字用其他字体不受影响
  → 视觉上「中文凭空消失、版式仍在」（即用户看到的乱码）
```

这也解释了两个现象：
- 为什么只有「文档类」PDF 受影响——扫描型漫画 PDF 没有文本层，不存在字体问题；
- 为什么 WPS 正常——常见推断是 WPS 内置 Adobe CJK CMap 数据或走系统字体回退（本节为推断，未对 WPS 做逆向验证；其余内容均为源码与实测事实）。

### 三、实测对照（Node + pdfjs-dist 4.10.38，加载该书第 3 页目录页）

| 条件 | pdf.js 告警 | 目录页可提取中文 |
| --- | --- | --- |
| `getDocument({ data })`（= IReader 现状） | `loadFont - translateFont failed: Ensure that the cMapUrl and cMapPacked API parameters are provided.` | 0 个 |
| `getDocument({ data, cMapUrl: '<pdfjs-dist>/cmaps/', cMapPacked: true })` | 无告警 | 25 个（"目录 / 整数 / 数学归纳法 / 抽屉原理 / …"，与 WPS 截图一致） |

### 四、修复实现（20261015 落地）

1. `electron/services/protocol.ts`：`ireader://` 协议新增 `pdfjs` host——`ireader://pdfjs/{cmaps|standard_fonts}/{文件名}`，白名单正则校验（仅单层文件名、连续点号不匹配，杜绝路径穿越），从 `<APP_ROOT>/node_modules/pdfjs-dist` 用 fs 读取（兼容 asar 内文件）并以 CORS 头返回；
2. `src/services/pdf.ts`：`getDocument` 传入 `cMapUrl: 'ireader://pdfjs/cmaps/'`、`cMapPacked: true`、`standardFontDataUrl: 'ireader://pdfjs/standard_fonts/'`，并以自定义 `CMapReaderFactory` / `StandardFontDataFactory`（主线程用 fetch 加载，替代 pdf.js 对非 http(s) 地址的 XHR 回退）接管资源加载；
3. 验证：`npm run typecheck` 与 `npm test` 通过；Node 端以相同参数与自定义工厂加载本书目录页——告警归零、25 个中文文本恢复（与 WPS 一致）。
